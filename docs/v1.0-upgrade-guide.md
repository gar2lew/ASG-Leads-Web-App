# v1.0 Upgrade Guide

Release: v1.0 Internal Production Release Candidate
Date prepared: 2026-07-06
Branch: `goal/v1-release-candidate`

## Purpose

This guide prepares ASG CRM operators, admins, and reviewers for the move from the current review-ready state to v1.0 internal production use.

This guide does not approve deployment. It defines the human and technical checks required before deployment can be considered.

## Upgrade Summary

v1.0 is a controlled internal production readiness release. It focuses on stabilisation, staff workflow, validation, release governance, documentation, UAT, and risk visibility.

It is not a public launch and it does not include live Salestrail rollout, production migrations, broad AI automation, client portal, or ASG-X.

## User Impact

### Reps

- Better workflow orientation across dashboard, lead queue, lead detail, next actions, notes, calls, callbacks, follow-ups, appointments, and mobile lead work.
- Staff UAT must confirm that daily lead work is clear and reliable.

### Managers

- Clearer reporting rhythm and daily performance review context.
- Manager UAT must confirm reports, client context, deal pipeline, and follow-up signals are trusted enough for internal use.

### Admins

- Clearer separation between routine admin work and governed production-sensitive controls.
- Admin UAT must confirm roster, permissions, system health, release metadata, settings history, and risky controls are understandable.

### Directors

- Release pack provides visibility into validation, risks, rollback, known issues, UAT, and go/no-go criteria.
- Director review should focus on whether residual risks are acceptable for internal production use.

## Technical Upgrade Steps

These steps are for a release manager after human approval. Do not run deployment steps until approval is granted.

1. Confirm branch and commit:

```powershell
git status --short
git branch --show-current
git log --oneline -10
```

2. Confirm Firebase target without deploying:

```powershell
Get-Content .firebaserc
Get-Content firebase.json
```

3. Re-run validation:

```powershell
npm run typecheck
npm run lint
npm test
npm run test:emulator:preflight
npm run test:emulator:rules
npm run test:emulator:firestore-smoke
npm run test:emulator:callables-dry-run
npm run build
cd functions
npm run build
npm run test:settings-admin
cd ..
git diff --check
```

4. Confirm UAT evidence:

- Feedback forms complete.
- Issue list triaged.
- Zero unresolved Critical issues.
- Zero unresolved High issues without approved workaround.
- Release owner sign-off recorded.

5. Confirm backup and rollback evidence:

- Firestore export plan approved.
- Storage backup approach approved.
- Rollback owner assigned.
- Hosting, Functions, rules, indexes, and data rollback paths understood.

6. Confirm deployment surface approval:

- Hosting only, if approved.
- Functions only, if approved.
- Firestore rules only, if approved.
- Firestore indexes only, if approved.
- No migration, Salestrail live sync, or phone backfill write unless separately approved.

## Data and Firebase Upgrade Notes

- `.firebaserc` points to `amplify-leads-2026`, which is production-like.
- `firebase.json` includes hosting, Functions, Firestore rules, and Firestore indexes.
- An unscoped `firebase deploy` has broad blast radius and must not be used casually.
- Phone normalisation and migration tooling remain dry-run-first and approval-gated.
- Salestrail live sync remains blocked until approved with reconciliation.

## Staff Preparation

Before internal production use:

1. Give reps the relevant sections of `docs/ASG-CRM-User-Manual.md`.
2. Give admins the relevant sections of `docs/ADMIN_BOOKLET.html`.
3. Run UAT scripts from `docs/staff-uat-plan.md`.
4. Record guide mismatches and update docs before launch if they affect core work.
5. Confirm support owner and issue escalation path.

## Post-Upgrade Monitoring

For the first operating window, monitor:

- Login and PIN failures.
- Lead saves.
- Call logging.
- Callback and follow-up queues.
- Appointment creation.
- Admin settings updates.
- Firestore permission errors.
- Functions errors, if Functions were deployed.
- Offline queue failures.
- Staff feedback.
- Release metadata shown in admin settings.
