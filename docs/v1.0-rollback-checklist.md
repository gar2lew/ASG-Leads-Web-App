# v1.0 Rollback Checklist

Release: v1.0 Internal Production Release Candidate
Date prepared: 2026-07-06
Branch: `goal/v1-release-candidate`

## Purpose

This checklist defines rollback preparation for v1.0. It does not approve rollback or deployment commands. Production rollback actions require release owner approval because they can affect live staff access and Firebase resources.

## Rollback Principles

- Prefer reversible release steps.
- Roll back one surface at a time where possible.
- Do not rewrite shared Git history.
- Do not force-move tags without explicit approval.
- Data rollback requires backup/export evidence.
- Firestore rules and Functions rollback are production-impacting and must be approved.

## Local Branch Rollback

Use only for local release-candidate work before merge:

```powershell
git switch goal/v1-release-candidate
git reset --hard savepoint-before-v1-release-candidate
```

This does not affect production Firebase resources.

## Merge Rollback

If the release candidate has been merged and the safest path is a Git revert:

```powershell
git switch codex-foundation
git log --oneline -10
git revert -m 1 <merge-commit>
```

Requirements:

- Confirm merge commit.
- Confirm revert target branch.
- Run validation after revert.
- Create review PR if required by branch policy.

## Tag Rollback Policy

Do not force-move release tags without explicit approval.

If a tag points to the wrong commit, prefer a corrected tag name:

```powershell
git tag release/v1.0-internal-rc2 <correct-commit>
```

Only push tags after human approval.

## Hosting Rollback

Use only after approved hosting deployment.

Preparation:

- Record current hosting release.
- Record previous known-good release.
- Confirm who can operate Firebase Hosting rollback.
- Confirm staff communication plan.

Rollback options:

1. Use Firebase Hosting release history in Firebase console.
2. Redeploy previous known-good build from a verified commit.

Required after rollback:

- Smoke test login.
- Smoke test dashboard.
- Smoke test leads.
- Confirm release metadata.
- Record incident and rollback time.

## Functions Rollback

Use only after approved Functions deployment.

Preparation:

- Record deployed Functions list before release.
- Record expected Functions exports.
- Confirm previous known-good commit.
- Confirm secrets remain unchanged.

Rollback options:

1. Deploy Functions from previous known-good commit.
2. Deploy corrective Functions fix after review.

Required after rollback:

- Run Functions build.
- Run callable tests where possible.
- Check Firebase Functions logs.
- Confirm callables used by login, settings, phone dry-run, and Salestrail config are stable.

## Firestore Rules Rollback

Use only after approved rules deployment.

Preparation:

- Store previous rules file in Git.
- Run emulator rules tests before rollback deployment.
- Confirm rules rollback does not reopen a known data exposure.

Rollback command, only after approval:

```powershell
firebase deploy --only firestore:rules
```

Required after rollback:

- Confirm login.
- Confirm lead reads and writes.
- Confirm `salestrailCalls` direct reads and writes remain denied.
- Confirm settings history and audit writes remain server-authoritative.

## Firestore Index Rollback

Index rollback can be slow and may not be immediate.

Preparation:

- Record added, changed, or removed indexes.
- Confirm query dependency before removing an index.
- Avoid index changes during emergency rollback unless the index itself is the problem.

Required after index rollback:

- Monitor index build or deletion status.
- Smoke test affected queries.
- Record any degraded workflow.

## Data Rollback

Data rollback is blocked unless a backup/export exists and the release owner approves the action.

Required before any data rollback:

- Confirm affected collection or Storage path.
- Confirm backup/export location.
- Confirm restore method.
- Confirm sample restore in disposable environment where practical.
- Confirm owner and approver.
- Confirm staff communication plan.

Data rollback is required for:

- Migrations.
- Phone normalisation write mode.
- Lead import full replace.
- Bulk destructive actions.
- Any unexpected production data corruption.

## Salestrail Rollback

Live Salestrail sync is not approved for v1.0.

If a future approved Salestrail live sync must be rolled back:

- Stop further sync.
- Identify import batch ID.
- Reconcile returned count to `salestrailCalls` document count.
- Preserve raw audit data.
- Do not delete imported calls until rollback plan is approved.
- Prefer marking batch status over destructive deletion unless approved.

## Phone Normalisation Rollback

Phone normalisation write mode is not approved for v1.0.

If future write mode is approved:

- Require backup/export before run.
- Record affected count and sample.
- Record old and new phone values.
- Reconcile post-run.
- Use backup/export for rollback if required.
